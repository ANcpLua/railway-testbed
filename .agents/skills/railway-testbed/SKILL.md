# Railway testbed

Each backing service the tests use runs on Railway as one sleeping service behind a TCP proxy. The
tests read its connection string from one owner-only env file and retry while it wakes. The pattern
and its measurements: https://github.com/ANcpLua/railway-testbed (README). Railway operations
follow the `use-railway` skill.

## Contract

- **Project and prefix:** Railway project `<repo>-testbed`, key prefix `<REPO>_TESTBED`, named
  partial in `.railway/railway.ts`.
- **Env file:** `~/.config/vitals/<repo>-testbed.env`, `chmod 600`, `KEY=value` lines, no quotes,
  no `export`, registered in Vitals as "<repo>-testbed connection strings (Railway <repo>-testbed)"
  (use the `vitals-keys` skill). Keys: `<PREFIX>_<SERVICE>_URL` per service, in the form the tests'
  client library takes; `<PREFIX>_<SERVICE>_<PART>` when one value is not enough;
  `<PREFIX>_WAKE_SECONDS_MAX`.
- **Wake budget:** `<PREFIX>_WAKE_SECONDS_MAX=120`. A slept service answers within 10 s, a fresh
  container within 25 s; the rest covers an image pull on another host. Fixtures retry for exactly
  this long, reading the key, never a literal.
- **Secrets:** 32 random letters and digits, generated by `provision.sh`, held only as Railway
  variables (`preserve()` in the partial) and in the env file.
- **Service shape:** `backing()` from the template: public image, `sleepApplication: true`, one
  replica, a CPU and memory ceiling, `tcp: [port]`, no volume, no HTTP domain. A process that sends
  outbound traffic on its own (telemetry, update checks) never sleeps: turn it off in the start
  command.

## Running tests against an existing testbed

A repository with `eng/testbed/` has one already; use it, never recreate it to run tests.

- Connection strings come from `~/.config/vitals/<repo>-testbed.env`. No local container,
  docker compose or Testcontainers fixture is a fallback, not even for one test.
- Wake the services required by the selected tests and wait for their real query checks to
  pass. Use an existing probe selector when available; otherwise the bundled probe checks all
  declared services. Let its configured wake budget finish and preserve the output. Do not
  duplicate a healthy probe or restart it because a fixed time elapsed.
- A failing probe names the service. Inspect its deployment state, bounded logs, connection
  settings and measured wake time before retrying or changing infrastructure. Provisioning
  preserves existing services and secrets, creates missing ones and applies the declared
  configuration; review that plan before using it to repair a verified configuration defect.
  A missing or stale local env file can be refreshed with `eng/testbed/provision.sh env` when
  the existing services and secrets are present. Do not recreate a project to diagnose a timeout.
- A test that times out on connect after a green probe is a wake-budget question: raise
  `<PREFIX>_WAKE_SECONDS_MAX` only when the probe measured a slower wake, and update the README
  table with the new time.

## Steps

1. **Inventory.** List every container the tests start: compose files, Testcontainers fixtures,
   `docker run` in scripts, CI `services:`. Done when each is either a backing service (image,
   port, password variable, client connection-string form) or stays with a written reason; an
   image the build itself produces and runs (a container smoke of the repo's own artifact) stays,
   and runs where a daemon is native (CI).
2. **Copy.** From the template repository: `.railway/railway.ts` and `.railway/package.json`,
   `eng/testbed/provision.sh`, `eng/testbed/probe.ts` and `eng/testbed/package.json`; add
   `node_modules/` to `.gitignore`. An existing `.railway/railway.ts` keeps its own services: the
   testbed goes into a separate Railway project and partial.
3. **Name.** `PROJECT` and `PREFIX` in provision.sh and probe.ts, `project(...)` and the header
   in railway.ts. Done when `grep -rn -e example-testbed -e EXAMPLE_TESTBED .railway eng/testbed`
   prints nothing.
4. **Declare.** Replace the examples: per service one `backing()` call, its password variables in
   `SECRETS`, its `render` line in `write_env`, its round trip (a write and read or a `SELECT`, never
   a port check) in `checks` and its keys in `KEYS`.
5. **Provision.** `railway init --name <repo>-testbed` (or `railway link --project <repo>-testbed`),
   `bun install --cwd .railway`, `eng/testbed/provision.sh`. Done when
   `railway config plan --detailed-exit-code` exits 0 and `bun eng/testbed/probe.ts` prints `ok`
   for every service.
6. **Wire.** Point the test fixtures at the keys, retrying each connection until it answers or the
   wake budget runs out; a missing env file fails with a message naming `eng/testbed/provision.sh`.
   Delete the compose services and container fixtures the testbed replaced.
7. **Document.** A README section: the service table (service, image, what uses it, limits, wake
   time from the probe), the env-file keys, the probe and recreate commands.

Done when the probe is green, the plan exits 0, the tests pass against the testbed with no container
daemon running, and no replaced container remains in the repository.

## Remote execution

The testbed supplies databases and brokers; it does not move a local test runner to Railway.
`railway run` supplies Railway variables to a local process. For remote Linux builds or checks,
use the existing `use-railway` sandbox workflow or a deliberately configured job. Pin the same
toolchain and dependencies, retain the exact source identity and results, and stop owned compute
after completion. Keep macOS/Windows checks on matching hosts and container-image checks on a
host with a real container daemon. Reuse already-valid results rather than running unrelated
suites just to keep services busy.
